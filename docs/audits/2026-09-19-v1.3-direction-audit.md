# SentinelPy v1.3 direction audit

**Date:** 2026-09-19  
**Baseline:** `main` at tag **v1.2.1**  
**Scope:** Product and technical direction only (no v1.3 implementation in this document).

---

## 1. Executive summary

SentinelPy is a **credible v1.x product** for its niche: authorized, read-only, single-URL HTTP security header review with a **safe report contract**, stable CLI exit codes, and reproducible CI. The codebase is small (~700 LOC core), stdlib-only at runtime, and well tested (~96 tests, ~89% coverage).

**No P0 or P1 defects** were confirmed on this pass that require an immediate patch before planning v1.3.

The highest-value near-term work is **contract hardening and operator/CI trust** (tests + docs), not new scan categories.

## 3. User workflow assessment

| Stage | Experience | Gaps |
| --- | --- | --- |
| **Install** | `pip install -e .` or GitHub Release wheel; no runtime deps. | No PyPI (intentional); GitHub-only install path must stay documented. |

| **Errors** | Fixed messages; stderr on CLI for error category. | Operators cannot see *why* TLS failed (by design — safe). |
| **Diagnosis** | Exit code + JSON `error.category` + empty findings on error. | v1.2.1 schema tests strengthen trust. |

## 4. Public API and report-schema evolution

**Stable public surface** (`sentinelpy.__init__`): `run_scan`, `ScanOptions`, `ScanReport`, `render_json`, `normalize_target_url`, `redact_url`, `__version__`, exceptions, `REPORT_SCHEMA_VERSION`.

**Subpackage `sentinelpy.checks`:** dual export (`evaluate_security_findings` + deprecated `evaluate_presence_findings`) until 2.0.

**Schema:** `report_schema_version: "1.0.0"` unchanged since v0.2.0b. README promises semver: patch/minor additive only; major may break.

**Recommended evolution:**

- **v1.2.x:** additive **tests only** + optional doc/schema clarifications (no new required JSON fields).
- **v1.3.0:** additive **documentation / CI artifacts** and optional CLI flags that do not change default JSON shape.
- **v2.0.0:** remove presence module, optional `report_schema_version: "2.0.0"` if evidence or finding model is tightened.

## 5. Security correctness (within scope)

| Topic | Assessment |
| --- | --- |
| **Redaction** | URL userinfo/query keys; CSP not in evidence excerpts; sensitive header names blocked. |
| **Redirects** | Final scheme for HSTS; redirect hops redacted in reports; cross-host redirect possible (documented). |
| **False negatives** | Missing headers → fail; invalid XFO/referrer/HSTS → warning; HTTP HSTS → advisory warning. Acceptable for “configuration hint” tool. |
| **False positives** | Strict quality rules (e.g. unrecognized Referrer-Policy → warning) reduce “green” scans. Preferable to false certainty. |
| **TLS** | Verification always on; no insecure opt-out. |

## 7. Decision: completed-report schema edge cases

**Question:** v1.2.2 patch vs v1.3?

**Decision: treat as v1.2.2 (patch), not v1.3.**

| Criterion | v1.2.2 patch | v1.3 minor |
| --- | --- | --- |
| User-visible behavior | Unchanged | Implies feature/theme release |
| API / JSON schema | Unchanged | Usually marketed as capability bump |
| Work type | Add parametrized jsonschema tests for `summary.status` ∈ {`passed`, `warning`, `failed`}, non-200 completed, multi-hop redirects | Same tests could ship in v1.3 but would dilute “minor” semver meaning |
| Risk | Low; dev-only `jsonschema` | N/A |

**Recommended v1.2.2 scope (when executed):**

- Schema-valid completed reports for: missing required headers on HTTPS (`summary.status=failed`; `summarize_findings()` prefers any `fail` over warnings), an advisory **warning** case that does not rely on missing headers (for example HTTP with the other four headers present so only HSTS is `warning`), HTTP 404/500 completed, multiple redirect hops.
- Assert summary counts align with findings.
- No new headers, no CLI flags, no schema file version bump.

**v1.3 should not be justified by tests alone** — it should deliver an operator/CI-facing capability (see below).

## 8. Three possible v1.3 directions (with trade-offs)

### Direction A — **CI & contract trust pack** (recommended)

**Content:** Consumer-facing docs (`docs/ci-github-actions.md` or README section), golden JSON fixtures checked into repo, optional composite workflow template, schema tests for all completed summary states (may land partly in v1.2.2), document exit-code vs `summary.status` matrix for pipelines.

| Pros | Cons |
| --- | --- |
| Matches primary audience (DevOps / app owners) | Less “exciting” than new checks |
| Zero runtime deps; stays read-only | Docs maintenance |
| Reinforces safe-report brand | Does not increase scan depth |

### Direction B — **Operator UX (CLI ergonomics)**

**Content:** Optional `--quiet` (suppress non-error stdout), config file for defaults (timeout, format, `--no-redirects`), shell completion optional.

| Pros | Cons |
| --- | --- |
| Daily-use comfort | Config file scope creep risk |
| Still one URL per invocation | Must not store secrets in config |
| | Harder to test cross-platform |

### Direction C — **Deeper semantics on the same five headers**

**Content:** Read-only evaluation of CSP-Report-Only, `frame-ancestors` vs XFO consistency hints, HSTS preload/includeSubDomains as **info** only.

| Pros | Cons |
| --- | --- |
| More “security tool” feel | Easier to introduce false certainty |
| No new HTTP surface if still one GET | Evidence/redaction review per new signal |
| | Users may expect OWASP parity |

---

## 9. Recommended direction

**Choose Direction A: CI & contract trust pack.**

**Why:** SentinelPy’s differentiation is **safe, honest, single-shot reports** for authorized checks—not breadth of attack surface. v1.2.x already fixed safety and schema errors; the next user-visible pain is **integrating scans into CI/CD confidently**. Direction A strengthens that without violating scope. Direction B is a reasonable **v1.3.1 or v1.4** follow-up; Direction C should wait until evidence rules are formally versioned (likely 2.0).

**Suggested v1.3.0 deliverables (when implementation starts):**

1. Documented GitHub Actions (and generic shell) patterns using JSON output + exit codes.
2. Checked-in golden report fixtures (completed warning/failed + error) validated in CI.
3. README “Integrating with CI” section with explicit non-goals reminder.

**Defer to v1.2.2:** parametrized completed-report jsonschema tests (can ship before v1.3 without feature fanfare).
